계획대로 **측정 → 판정 → 구현** 중 1·2단계다. 구현은 안 했다.

## 이름 길이 기준을 왜 4자로 했나

처음 센 값은 **89쌍**이었다. 눈으로 보니 셋이 섞여 있었다.

```
자기·계열   대한전선 → 대한전선 · (주)LS → LS ELECTRIC
이름 변형   한국전력 + 한국전력공사(주) 가 따로 세어짐 (Company/Stock 두 행)
짧은 이름   GS · NC · LS · KT 가 300자 창에서 아무 데나 걸린다
             롯데에너지머티리얼즈 → "NC, GS" 가 대표적인 소음
```

정규화(괄호·주식회사·공백 제거) + 자기 포함관계 제외 + 최소 길이로 다시 세면:

| 최소 길이 | 실명 지목 | 고유 쌍 |
| ---: | ---: | ---: |
| 2자 | 18 / 40 | 61 |
| 3자 | 16 / 40 | 39 |
| **4자** | **16 / 40** | **37** |
| 5자 | 14 / 40 | 25 |

4자에서 목록이 읽히기 시작하고 5자에서는 **기아·우진** 같은 진짜 거래처가
빠진다. 그래서 4자를 보고 값으로 쓰되, **이건 임계이지 해법이 아니다**(아래).

## 2단계 판정 — **구현할 값어치가 있다**

근거 넷:

1. **수율이 충분하다.** 40% · 37쌍. 182곳으로 넓히면 대략 73곳 · 170쌍이고,
   그러면 그래프에 **인과 술어가 처음 생긴다**(지금 accepted 0)
2. **배관이 이미 다 있다.** `SUPPLIES`·`CUSTOMER_OF` 정책 · 빌더 ·
   `analytics.firm_supply_relation` 테이블 전부 존재하고 데이터만 0행이다
3. **지어내기가 구조적으로 막혀 있다.** 빌더가
   `absenceSemantics: unknown_not_disclosed` 라 공시가 없으면 아무것도 안 만든다
4. **읽히는 것이 나온다.** 위 목록은 전부 사람이 확인 가능한 관계다

## 구현 전에 반드시 풀어야 할 것 — 이름 해소

**부분 문자열 매칭으로는 못 만든다.** 위 4자 임계는 측정을 읽으려고 쓴 것이지
빌더의 규칙이 될 수 없다. 남는 문제 셋:

- **계열사·모회사**: `(주)LS → LS일렉트릭` 은 거래처가 아니라 자회사다.
  `엘에스일렉트릭 → LS ELECTRIC` 은 같은 회사의 다른 표기다
- **지주사 보고서**: 포스코홀딩스의 목록은 포스코퓨처엠 것을 포함한 것으로
  보인다. 지주사 사업보고서는 자회사 사업을 함께 서술한다
- **짧은 이름**: `기아`(2자)는 진짜인데 `GS`(2자)는 소음이다. 길이로는 못 가른다

필요한 것은 **별칭 테이블 + 소유관계 제외 + 지주사 보고서의 섹션 귀속**이고,
이게 이 작업의 실제 비용이다. 수집은 이미 되는 것을 확인했다(80요청 · 오류 0).

# E2 — 짧은 이름을 쟀다 (2026-08-06). 별칭 테이블이 답이 아니다

위에서 *"`기아`(2자)는 진짜인데 `GS`(2자)는 소음이다. 길이로는 못 가른다"* 로
남겨둔 질문이다. 계획은 답을 **별칭 테이블**로 예상했다. 재보니 아니었다.

**먼저 정정**: 계획에 "유니버스 648개 이름" 이라고 적었는데 그 648 은 `fred:DEXKOUS`
관측 겹침(648/675)에서 옮겨온 무관한 수다. 실제 카탈로그는 **297** 이다
(`core.entity` Company 중 `core.security_issuer_identity` 를 가진 것. Company 자체는
325 이므로 28은 발행사 신원이 없다).

## 4자 미만은 34 / 297 (11.4%)

```
정규화 길이  1자  1     2자 12     3자 21      → 34
```

`normalizeCompanyName` 은 `(주)`·`주식회사`·`㈜`·`(유)`·`유한회사`·공백을 지운다.

## 위험은 길이가 아니라 문자 체계로 갈린다

각 짧은 이름이 카탈로그의 **다른** 이름 안에 부분 문자열로 몇 번 들어가는지 셌다.
이것이 `(주)LS` 가 `wolseley` 에 걸렸던 결함의 직접 측정이다.

```
라틴 10개   충돌 있음 5   총 충돌 76
한글 24개   충돌 있음 5   총 충돌  7
```

라틴이 위험한 이유는 라틴 부분 문자열이 더 긴 라틴 단어 안에 숨기 때문이다.

```
t   → 66건   alphabetinc · citigroupinc · intelcorp · tesla,inc. …
lg  →  4건   high-trendinternationalgroup · lg전자 · lg화학 · lg유플러스
sk  →  3건   novonordiskas ← nordi-SK-as · sk이노베이션 · sk텔레콤
ls  →  2건   appliedmateria-LS-inc/de · we-LS-fargo&company/mn
gm  →  1건   fi-GM-a,inc.
```

한글 충돌 7건은 **전부 자기 확장형**이다.

```
카카오 → 카카오뱅크      케이티 → 케이티앤지      효성 → 효성중공업
두산   → 두산에너빌리티 · 두산테스나 · 두산퓨얼셀      테스 → 두산테스나
```

이것들은 **가려짐(shadowing)** 이고, 해소기의 "서로 부분 문자열이면 긴 쪽이 이긴다"
규칙이 이미 처리한다. `테스` 대 `두산테스나` 도 서로 다른 회사지만 같은 규칙으로
긴 쪽이 이긴다.

충돌 0: 라틴 5(`aal`·`hca`·`nok`·`oci`·`vz`), **한글 19**(`기아`·`네이버`·`넷마블`·
`녹십자`·`하이브`·`종근당`·`코웨이`·`팬오션`·`펩트론`·`큐라클`·`유니드`·`이노션`·
`제너셈`·`코세스`·`비나텍`·`브이엠`·`우진`·`풍산`·`엔씨`).

## 결론 — `MIN_MENTION_LENGTH` 는 두 문제를 하나로 뭉친 것이다

지금 규칙은 **라틴 5개를 막으려고 충돌 0인 한글 19개를 버린다.** 그중 `기아` 는
이 문서가 처음부터 지목한 진짜 거래처다.

별칭 테이블은 답이 아니다. 별칭을 만들어도 `기아` 는 여전히 2자이고, 정확 일치를
허용할지 말지의 판단 기준이 없으면 같은 질문이 되돌아온다. 기준은 **문자 체계와
충돌 수**이고 둘 다 카탈로그에서 계산된다 — 손으로 관리할 표가 필요 없다.

그리고 라틴의 근본 원인은 길이가 아니다. **정규화가 공백을 지워서 토큰 경계를
없앤다.** 경계가 없으면 포함 검사밖에 할 수 없고, `figma` 는 `gm` 을 담는다.
`MIN_MENTION_LENGTH` 는 정규화가 만든 문제에 붙인 반창고다.

## 그래서 무엇을 할 것인가 — B4 와 함께 설계한다

계획이 E2 를 B 앞에 둔 이유가 *"해소기를 두 번 고치지 않기 위해"* 였다. 그 판단대로
지금 코드를 바꾸지 않고, B4(계열회사 절)가 해소기를 열 때 함께 넣는다. 설계 입력은
이렇게 확정한다.

- **한글 이름은 길이 제한을 두지 않는다.** 충돌 19/24가 0이고 나머지 7건은 기존
  가려짐 규칙이 처리한다. 얻는 것이 `기아`·`카카오`·`네이버` 급이다
- **라틴 이름은 포함 검사를 쓰지 않는다.** 길이를 늘려도 안전해지지 않는다
  (`aal`·`nok` 은 3자에 충돌 0, `gm` 은 2자에 충돌 1). 토큰 경계가 필요하고, 그러려면
  공백을 지우지 않는 두 번째 정규화 형태를 함께 들고 다녀야 한다
- **`t` 는 어떤 규칙으로도 못 쓴다.** 66건과 충돌한다. 카탈로그에서 제외하고 그
  사실을 수치로 남기는 것이 맞다
