## 지금 바로 이어서 할 것 — 거시 상관 2·3·4단계

로드맵 2b. **1단계는 끝났다**(커밋 `445d361`): 13개 FRED 계열이 `core.entity`
(`entity_type='Metric'`)와 `FRED_SERIES` 식별자를 갖고, `analytics.macro_series_topic`
이 계열을 시장 뉴스 주제에 잇는다.

### 왜 이걸 하는가

미귀속 2,454건과 어휘 매칭 88건이 **어디에도 닿지 않는다.** 거시 데이터는
`market.macro_vintage` 에 55,775행 13계열이 2014년부터 쌓여 있는데 그래프와
완전히 분리돼 있다. 이걸 이으면 "종목 이름 없는 시장 뉴스가 종목에 닿는 길" 이
처음 생긴다.

**얻지 못하는 것을 먼저 안다**: 이건 통계적 엣지이고 `SAME_ETF_BASKET` 과 같은
층위다. 인과가 아니다. 상관을 인과로 읽히게 표시하면 안 된다.

### 2단계 — 정책

`apps/api/src/relations/relation-policy.ts` 의 `RELATION_BUILDER_POLICIES` 에
술어를 더한다. `PRODUCT_SIMILARITY` 항목을 그대로 본뜨면 된다.

```
relationClass: 'association'
requiresModelConfig: true      ← 이게 핵심. 설정을 묶어야 통과한다
minSourceRevisions: 1
superhubDegreeCap: 필요        ← 13계열 × 330종목이면 계열 하나가 초대형 허브가 된다
promotionEligible: true
absenceSemantics: 'unknown_not_disclosed'
```

술어 이름은 인과로 읽히지 않아야 한다. `AFFECTS` 나 `EXPOSES` 같은 이름을 쓰면
안 된다 — 측정한 것은 "함께 움직였다" 뿐이다.

온톨로지에도 있어야 한다. `knowledge.predicate_ontology_revision` 에
`policy_status='approved'` 로 없으면 `persistRelationCandidates` 가 거부한다.
`approvedOntologyIds()` 가 읽는 곳이다.

### 3단계 — 빌더

`apps/api/src/relations/builders/` 에 추가. `product-similarity.ts` 와
`product-similarity-model.ts` 의 **분리를 따른다** — 모델 계산과 후보 생성이
별개 파일이다.

재료:

```
market.macro_vintage        55,775행 · 13계열 · 2014-01 ~ 2026-07
market_ts.ohlcv(주식 1D)    298,754행 · 330종목 · 2021-07 ~ 2026-08
겹치는 구간                 약 5년
```

`market_ts.ohlcv` 는 **research-common 소유**다(`database-ownership.md`). 읽기만
한다. `domain='stock' AND timeframe='1D'` 로 걸러야 한다.

`macro_vintage` 는 vintage 테이블이다 — 같은 `observation_date` 에 여러 realtime
버전이 있다. 어느 버전을 쓸지 정하고 그 규칙을 `model_config` 에 적어야 한다.
과거 시점에 알 수 없던 개정치를 쓰면 미래를 보는 것이 된다.

**`model_config` 에 반드시 묶을 것**: 창 길이 · 상관 임계값 · 계열 id ·
수익률 정의 · 표본 최소 길이 · vintage 선택 규칙. 하나라도 빠지면 재실행이
안 되고, 재실행이 안 되면 반박할 수 없고, 반박할 수 없으면 그건 주장이다.

### 4단계 — 배선

`apps/api/src/analytics/run-v2-graph-publish.ts`. 기존 세 빌더
(`buildEtfBasketCandidates`·`buildOfficialSectorCandidates`·
`buildProductSimilarityCandidates`)가 호출되고 `persistRelationCandidates` 로
저장되는 자리 옆에 붙인다. 요약에 후보 수를 accepted/quarantined 로 나눠 남길 것 —
합계 하나로는 무엇이 일어났는지 안 보인다.

## 이번 세션에 실제로 낸 오류 — 같은 순서로 틀리지 않도록

`handoff-2026-08-03.md` 의 7가지에 더해:

1. **`public.etf_holdings.entity_id` 는 `public.entities` 공간이다.** `core.entity`
   와 비교해 "419쌍이 새 연결" 이라는 좋아 보이는 결과를 냈고 전부 틀렸다.
   파이프라인은 `entity_key` → `core.entity_identifier` 로 변환한다. 오류 5번의 재발
2. **백필 조건을 출신이 아니라 현재 값으로 걸 것.** 마이그레이션 064 를 "macro
   시그널에서 온 것" 으로 걸어 1,491행을 잡았는데, 초과한 13건은 텍스트 귀속이
   이미 올바르게 옮긴 것이었다. 올바른 작업을 되돌릴 뻔했다
3. **`UPDATE ... FROM` 의 JOIN ON 에서 갱신 대상 테이블을 참조할 수 없다.**
   상관 조건은 WHERE 로 보낸다
4. **증거 틀을 "지어내기 금지" 로 오해하지 말 것.** 이 저장소는 세 종류를
   허용한다 — `source_revision`(원문이 말한다) · `model_config`(모델이 만들었고
   설정을 묶었다) · `identity_mapping`. `PRODUCT_SIMILARITY` 6,590건이 accepted 인
   것이 증거다. 나는 이걸 놓쳐 거시 상관을 한 번 잘못 기각했다
5. **파이프라인이 쓰는 입력 범위를 확인할 것.** ETF 는 티커별 **최신 as_of 한 장만**
   쓴다. 35일치 전부로 계산해 예측을 세웠다가 틀렸다
