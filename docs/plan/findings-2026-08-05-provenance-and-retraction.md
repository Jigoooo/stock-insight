# 두 가지 발견 — 출처 오기재와 철회 부재 (2026-08-05)

계획 1단계(계측기 복구)를 진행하다 원장에서 두 가지를 찾았다. **둘 다 내가 이번
세션에 만든 것이 아니고, 둘 다 내가 앞서 보고한 내용을 정정하게 만든다.**

---

## 1. 내부 스냅샷 다섯 종이 전부 ETF 출처로 적혀 있었다 — **고침**

### 원인

`run-v2-graph-publish` 는 슬롯마다 fetch run 을 다섯 개 연다. 멱등키가
`${naturalRunKey}:fencing-${token}` 이라 **프로바이더가 안 들어갔다.** 다섯이 같은
키를 만들고 `ON CONFLICT (idempotency_key) DO UPDATE ... RETURNING` 이 뒤에 부른
쪽 전부에게 **먼저 부른 쪽의 `source_id`** 를 돌려줬다.

### 잰 것 (고치기 전)

```
internal-etf-holdings-snapshot   798 transitional_company_profile
                                 171 transitional_etf_snapshot      ← 유일하게 자기 것
                                 119 transitional_industry_classification
                                  63 stock_price_window
                                  18 macro_series_window
나머지 내부 출처 4종                0 — 승인돼 있고 한 번도 안 쓰였다
```

관계 증거가 전량 ETF 를 가리킨다: `SAME_ETF_BASKET` 22,449 ·
`PRODUCT_SIMILARITY` 13,180 · `CLASSIFIED_AS` 119 · `MACRO_COMOVEMENT` 210.

`payload_metadata.http_meta.kind` 에 진짜 종류가 남아 있어 **내용은 유실되지
않았다.** 다만 증거 원장은 제품이 권위 있는 출처로 취급하는 것이고, 그게 전부
틀린 출처를 가리키고 있었다.

### 내가 처음에 오독한 것

**"이번 세션 거시 코드가 만든 결함" 으로 봤는데 틀렸다.** `transitional_company_profile`
798건은 내 작업보다 한참 앞선다. 이 잡이 존재한 이래 계속이었고 거시 코드는 같은
함정에 빠진 다섯 번째다.

### 고친 방법 (커밋 `abc627f`)

1. 멱등키에 프로바이더를 넣었다.
2. `OPEN_FETCH_RUN_SQL` 의 `ON CONFLICT` 에
   `WHERE fetch_run.source_id = EXCLUDED.source_id` 를 걸어, 키가 겹치고 출처가
   다르면 **행이 안 나오게** 했다. 조용한 오기재를 시끄러운 실패로 바꾼 것이다.

일회용 클론에서 롤백 트랜잭션으로 증명: 키 K 를 ETF 로 삽입 → source 30 /
같은 K 를 거시계열로 → **0행** / 같은 K 를 다시 ETF 로 → 30(멱등 유지).

### 소급 — 드라이런만 했다 (쓰기 없음)

```
옮길 것       998 리비전 · 464 정체성
충돌           0     UNIQUE(source_id, provider_record_key)
가드 위반      0     대상 계약 넷 다 승인 + effective_from ≤ available_at
영향 증거      13,509행 — FK 는 source_revision_id 라 안 깨진다
혼합 정체성    0     ETF 아래 484개가 전부 kind 하나씩 → 옮김이 모호하지 않다
```

두 계층을 건드려야 한다: `source_record_identity.source_id` 와
`source_revision.source_contract_revision_id`. **실행은 프로덕션 쓰기라 판단 대기.**

## 2. 원장에 철회가 없다 — **미해결. 앞서 한 보고를 정정한다**

### 내가 틀리게 보고한 것

베타 조정을 적용하고 **"거시 엣지 32 → 23, 가짜는 빠지고 진짜는 남았다"** 고
보고했다. **23은 그 실행의 수락 후보 수이지 그래프의 엣지 수가 아니다.**

### 실제 그래프 (스냅샷 22)

```
MACRO_COMOVEMENT identity   36
최신 리비전이 accepted       36  ← 전부
리비전 번호                  1, 2, 3
```

원유 엣지를 펼치면 베타 조정이 **걷어냈어야 할 것들이 옛 신뢰도 그대로 남아 있다**:

```
Alphabet       0.263      ← 베타 조정에서 임계 아래로 떨어진 것
Meta Platforms 0.254      ←
GS             0.291      ←
C              0.279      ←
포스코인터내셔널 0.298      ← 베타 조정이 새로 드러낸 것
현대로템        0.289      ←
SK이노베이션    0.251      ←
```

**스냅샷은 두 실행의 합집합이다.** 새 것이 더해졌을 뿐 옛 것이 안 빠졌다.

### 원인 — 설계이지 버그가 아니다

빌더가 후보를 안 내면 아무 일도 일어나지 않는다. 마지막 `accepted` 리비전이
그대로 최신이고, 스냅샷 선택기는 최신 리비전을 고른다. 철회 경로가 아예 없다.

```
술어                열린 구간 / 전체
MACRO_COMOVEMENT        73 / 73
PRODUCT_SIMILARITY   6,590 / 6,590
SAME_ETF_BASKET     17,146 / 17,146
```

**세 술어 전부 100% 열려 있다.** 이건 원장 전체의 동작이다.

### 뿌리는 `absenceSemantics` 다

```ts
export type AbsenceSemantics = 'unknown_not_disclosed' | 'closed_world';
```

`closed_world` 가 **타입에 이미 있는데 어떤 술어도 안 쓴다.**
`MACRO_COMOVEMENT` 는 `unknown_not_disclosed` 다.

그런데 이 술어에는 그게 맞지 않는다. 공시 기반 술어(`SUPPLIES`)는 공시가 없으면
**정말로 모르는 것**이다. 하지만 거시 상관은 **매일 모든 쌍을 전부 잰다.** 후보가
안 나온 것은 "모른다" 가 아니라 **"쟀고 임계 아래였다"** 이다. 정보가 있는
부재이고, 그게 `closed_world` 다.

`PRODUCT_SIMILARITY` · `SAME_ETF_BASKET` 도 같은 성격이다 — 전수 계산이다.

### 이것이 제품에 뜻하는 것

지금 그래프는 **자기 기준을 더 이상 만족하지 않는 엣지를 계속 들고 있다.**
거시 엣지 36개 중 13개가 그렇다(36%). 임팩트 경로는 그 엣지도 똑같이 밟는다.
즉 베타 조정의 이득 중 "가짜가 빠진다" 는 절반은 **아직 실현되지 않았다.**
드러난 절반(포스코인터내셔널·현대로템·SK이노베이션)만 실현됐다.

### 안 고친 이유

철회를 넣는 것은 **원장 의미를 바꾸는 결정**이고 세 술어에 동시에 영향을 준다.
선택지가 적어도 셋이다:

1. **`closed_world` 술어에 한해 전수 실행마다 미출현 identity 를 철회한다** —
   가장 옳아 보이지만 "전수 실행" 이 실패하거나 부분 실행되면 대량 철회가 난다.
   실행 완전성을 증명하는 장치가 먼저 필요하다
2. **스냅샷 선택기가 최신 실행의 리비전만 고른다** — 원장은 그대로 두고 그래프만
   현재를 반영한다. 값싸지만 원장과 그래프가 갈린다
3. **그대로 둔다** — 그래프가 "한때 성립했던 것" 의 누적임을 받아들인다.
   그렇다면 화면이 그렇게 말해야 한다

**근거 없이 고르지 않았다. 사용자 판단이다.**
