# 두 가지 발견 — 출처 오기재와 철회 부재 (2026-08-05)

계획 1단계(계측기 복구)를 진행하다 원장에서 두 가지를 찾았다. **둘 다 내가 이번
세션에 만든 것이 아니고, 둘 다 내가 앞서 보고한 내용을 정정하게 만든다.**

---

## 1. 내부 스냅샷 다섯 종이 전부 ETF 출처로 적혀 있었다 — **고침**

### 원인

`run-v2-graph-publish` 는 슬롯마다 fetch run 을 다섯 개 연다. 멱등키가
`${naturalRunKey}:fencing-${token}` 이라 **프로바이더가 안 들어갔다.** 다섯이 같은
키를 만들고 `ON CONFLICT (idempotency_key) DO UPDATE ... RETURNING` 이 뒤에 부른
쪽 전부에게 **먼저 부른 쪽의 `source_id`** 를 돌려줬다.

### 잰 것 (고치기 전)

```
internal-etf-holdings-snapshot   798 transitional_company_profile
                                 171 transitional_etf_snapshot      ← 유일하게 자기 것
                                 119 transitional_industry_classification
                                  63 stock_price_window
                                  18 macro_series_window
나머지 내부 출처 4종                0 — 승인돼 있고 한 번도 안 쓰였다
```

관계 증거가 전량 ETF 를 가리킨다: `SAME_ETF_BASKET` 22,449 ·
`PRODUCT_SIMILARITY` 13,180 · `CLASSIFIED_AS` 119 · `MACRO_COMOVEMENT` 210.

`payload_metadata.http_meta.kind` 에 진짜 종류가 남아 있어 **내용은 유실되지
않았다.** 다만 증거 원장은 제품이 권위 있는 출처로 취급하는 것이고, 그게 전부
틀린 출처를 가리키고 있었다.

### 내가 처음에 오독한 것

**"이번 세션 거시 코드가 만든 결함" 으로 봤는데 틀렸다.** `transitional_company_profile`
798건은 내 작업보다 한참 앞선다. 이 잡이 존재한 이래 계속이었고 거시 코드는 같은
함정에 빠진 다섯 번째다.

### 고친 방법 (커밋 `abc627f`)

1. 멱등키에 프로바이더를 넣었다.
2. `OPEN_FETCH_RUN_SQL` 의 `ON CONFLICT` 에
   `WHERE fetch_run.source_id = EXCLUDED.source_id` 를 걸어, 키가 겹치고 출처가
   다르면 **행이 안 나오게** 했다. 조용한 오기재를 시끄러운 실패로 바꾼 것이다.

일회용 클론에서 롤백 트랜잭션으로 증명: 키 K 를 ETF 로 삽입 → source 30 /
같은 K 를 거시계열로 → **0행** / 같은 K 를 다시 ETF 로 → 30(멱등 유지).

### 소급 — 드라이런만 했다 (쓰기 없음)

```
옮길 것       998 리비전 · 464 정체성
충돌           0     UNIQUE(source_id, provider_record_key)
가드 위반      0     대상 계약 넷 다 승인 + effective_from ≤ available_at
영향 증거      13,509행 — FK 는 source_revision_id 라 안 깨진다
혼합 정체성    0     ETF 아래 484개가 전부 kind 하나씩 → 옮김이 모호하지 않다
```

### 소급 시도 — **원장이 막는다. 못 한다**

승인을 받아 실행했고 트랜잭션이 첫 UPDATE 다음에 멈췄다:

```
UPDATE 998                                   ← raw_object 는 통과
ERROR: ingestion.source_record_identity is append-only; append a revision instead
CONTEXT: ingestion.reject_immutable_revision_mutation()
```

**롤백됐다. 프로덕션은 그대로다.**

세 표가 append-only 트리거를 달고 있다:

```
ingestion.source_contract_revision
ingestion.source_record_identity
ingestion.source_revision
```

즉 계보는 **설계상 불변**이다. 이건 결함이 아니라 원장의 핵심 보장이고,
소급으로 고치는 것은 "그때 이렇게 기록했다" 는 감사 기록을 지우는 일이다.

**내 드라이런이 이걸 못 잡았다.** UNIQUE·CHECK 제약과 FK 는 봤는데 **트리거를 안
봤다.** "충돌 0 · 위반 0" 이 "쓸 수 있다" 는 뜻이 아니었다. 다음에 쓰기 계획을
드라이런할 때는 `pg_trigger` 를 반드시 함께 볼 것.

### 그래서 남는 것

- `raw_object.source_id` 만 바꿀 수 있는데 **그것만 고치면 리비전 계약과 어긋나
  오히려 더 나빠진다.** 안 한다
- append-only 식으로 새 정체성·새 리비전을 덧붙이는 길은 있지만
  (`supersedes_source_revision_id` 가 있다), **관계 증거 13,509행은 여전히 옛
  리비전 id 를 가리킨다.** 그걸 맞추려면 증거 원장을 고쳐 써야 하고, 그건 잘못된
  포인터를 남겨 두는 것보다 나쁘다
- **결론: 과거는 그대로 둔다.** `payload_metadata.http_meta.kind` 가 진짜 종류를
  갖고 있으므로 판별은 가능하다. 2026-08-05 이후 실행부터 맞게 적힌다

## 2. 원장에 철회가 없다 — **미해결. 앞서 한 보고를 정정한다**

### 내가 틀리게 보고한 것

베타 조정을 적용하고 **"거시 엣지 32 → 23, 가짜는 빠지고 진짜는 남았다"** 고
보고했다. **23은 그 실행의 수락 후보 수이지 그래프의 엣지 수가 아니다.**

### 실제 그래프 (스냅샷 22)

```
MACRO_COMOVEMENT identity   36
최신 리비전이 accepted       36  ← 전부
리비전 번호                  1, 2, 3
```

원유 엣지를 펼치면 베타 조정이 **걷어냈어야 할 것들이 옛 신뢰도 그대로 남아 있다**:

```
Alphabet       0.263      ← 베타 조정에서 임계 아래로 떨어진 것
Meta Platforms 0.254      ←
GS             0.291      ←
C              0.279      ←
포스코인터내셔널 0.298      ← 베타 조정이 새로 드러낸 것
현대로템        0.289      ←
SK이노베이션    0.251      ←
```

**스냅샷은 두 실행의 합집합이다.** 새 것이 더해졌을 뿐 옛 것이 안 빠졌다.

### 원인 — 설계이지 버그가 아니다

빌더가 후보를 안 내면 아무 일도 일어나지 않는다. 마지막 `accepted` 리비전이
그대로 최신이고, 스냅샷 선택기는 최신 리비전을 고른다. 철회 경로가 아예 없다.

```
술어                열린 구간 / 전체
MACRO_COMOVEMENT        73 / 73
PRODUCT_SIMILARITY   6,590 / 6,590
SAME_ETF_BASKET     17,146 / 17,146
```

**세 술어 전부 100% 열려 있다.** 이건 원장 전체의 동작이다.

### 뿌리는 `absenceSemantics` 다

```ts
export type AbsenceSemantics = 'unknown_not_disclosed' | 'closed_world';
```

`closed_world` 가 **타입에 이미 있는데 어떤 술어도 안 쓴다.**
`MACRO_COMOVEMENT` 는 `unknown_not_disclosed` 다.

그런데 이 술어에는 그게 맞지 않는다. 공시 기반 술어(`SUPPLIES`)는 공시가 없으면
**정말로 모르는 것**이다. 하지만 거시 상관은 **매일 모든 쌍을 전부 잰다.** 후보가
안 나온 것은 "모른다" 가 아니라 **"쟀고 임계 아래였다"** 이다. 정보가 있는
부재이고, 그게 `closed_world` 다.

`PRODUCT_SIMILARITY` · `SAME_ETF_BASKET` 도 같은 성격이다 — 전수 계산이다.

### 이것이 제품에 뜻하는 것

지금 그래프는 **자기 기준을 더 이상 만족하지 않는 엣지를 계속 들고 있다.**
거시 엣지 36개 중 13개가 그렇다(36%). 임팩트 경로는 그 엣지도 똑같이 밟는다.
즉 베타 조정의 이득 중 "가짜가 빠진다" 는 절반은 **아직 실현되지 않았다.**
드러난 절반(포스코인터내셔널·현대로템·SK이노베이션)만 실현됐다.

### 안 고친 이유

철회를 넣는 것은 **원장 의미를 바꾸는 결정**이고 세 술어에 동시에 영향을 준다.
선택지가 적어도 셋이다:

1. **`closed_world` 술어에 한해 전수 실행마다 미출현 identity 를 철회한다** —
   가장 옳아 보이지만 "전수 실행" 이 실패하거나 부분 실행되면 대량 철회가 난다.
   실행 완전성을 증명하는 장치가 먼저 필요하다
2. **스냅샷 선택기가 최신 실행의 리비전만 고른다** — 원장은 그대로 두고 그래프만
   현재를 반영한다. 값싸지만 원장과 그래프가 갈린다
3. **그대로 둔다** — 그래프가 "한때 성립했던 것" 의 누적임을 받아들인다.
   그렇다면 화면이 그렇게 말해야 한다

**근거 없이 고르지 않았다. 사용자 판단이다.**

### 결정과 적용 (2026-08-05) — 1번을 골랐고 프로덕션에 반영됐다

사용자가 "가장 옳은 방법" 을 골랐다. 두 커밋으로 나눠 넣었다:

- `e73fca7` 선택기 — supersede 검사를 `IN ('accepted','rejected','superseded')` 로.
  `quarantined_unverified` 는 뺐다(3,312건이 있어 철회로 치면 수집이 한 번
  어긋날 때 그래프가 대량으로 비워진다)
- `6b55ada` 빌더 — 모델이 "겹침 충분 + 임계 미달" 만 `measuredBelowThreshold` 로
  담고, 퍼블리셔가 그 쌍의 기존 identity 에 `rejected` 를 덧붙인다

**부재로 철회하지 않는 것이 핵심이다.** 겹침 부족·미로드·차수 상한은 전부
철회 사유가 아니고, 테스트가 겹침 부족이 목록에 안 들어가는 것을 고정한다.

적용은 `--slot-suffix retract-1` 로 돌렸다(문서화된 재실행 방법 —
claim 행을 지우면 예정된 슬롯까지 풀린다).

```
                       적용 전        적용 후
스냅샷                  22             23
스냅샷 엣지             5,415          5,402
거시 엣지               36             23
rejected 리비전         0              13
경로가 참조하는 스냅샷   22             23
거시 스텝               304            222
거시 경로가 닿는 종목    10             8
술어 다양성   1종135·2종185·3종158·4종22 → 1종135·2종186·3종179
```

**36 − 13 = 23 으로 산술이 닫히고, 드라이런 예고(13)와 실제가 일치했다.**

원유 엣지에서 Alphabet · Meta · GS · C · ASML · GM 이 빠졌다. 남은 것은
에너지 섹터 ETF 0.580 · 엑슨 0.558 · 항공 · 포스코인터내셔널 · 현대로템 ·
SK이노베이션 — 전부 경제적으로 읽히는 것들이다.

**대가도 적는다.** 4종 술어를 밟던 사건 22건이 3종으로 내려갔고, 거시 경로가
닿는 종목이 10 → 8 로 줄었다. 엣지를 13개 지웠으니 당연하고, 그 13개는
오늘 측정으로 성립하지 않는 것들이다. **다양성이 줄어든 것이 아니라 근거 없는
다양성이 빠진 것이다.**

# D1 주제 엔티티 — 닫혔다 (2026-08-05)

`handoff-2026-08-05.md` 가 **"이 단계로는 못 닫는다"** 고 적어 둔 관측 2

## 사슬

```
마이그레이션 068   주제 엔티티 5 · MEASURED_BY approved · 전용 출처 1
귀속               125 매칭 = 42 귀속 + 5 모호 + 78 계열없음
그래프 (스냅샷 24)  MEASURED_BY 엣지 14 · 엔티티 656 → 670
경로                MEASURED_BY 스텝 279 · 주제 출발 경로 279
                   주제 사건 중 경로를 낸 것 38
```

**38 은 구현 전 예측과 정확히 같다** — rates 17 · energy 17 · fx 3 · growth 1.
엣지 수(14)도 매핑 행 수와 같다. 예측한 것과 잰 것이 어긋나지 않았다.

경로 모양: `topic:rates → 계열 → TLT`, 2홉. 설계한 그대로다.

## 왜 42이고 120이 아닌가

처음 잰 "미귀속 120건이 주제 하나에 걸린다" 는 어휘 기준이고, 068 은
`macro_series_topic` 에 있는 주제만 엔티티로 만든다. 어휘엔 7주제인데
`market`·`trade` 는 계열이 아예 없다(39+39=78).

**그건 누락이 아니라 §4 에서 이미 닫힌 측정이다** — FRED 에 관세를 대표하는
일간 계열이 없고, 모든 종목이 지수와 상관되므로 market 은 베타다. 그래서
노드를 만들지 않았고, 거부 사유를 `topic_has_no_series` 로 따로 세어
"마이그레이션 대기" 와 섞이지 않게 했다.

## 엔티티가 14 늘어난 이유

주제 5개 + **상관 엣지가 없던 계열 9개**다. 월간·주간이라 `MACRO_COMOVEMENT`
를 못 만들던 계열들이 `MEASURED_BY` 로 처음 그래프에 들어왔다. 종목에 닿지는
않지만 주제 아래 있다는 사실은 이제 그래프가 안다.

## 대가

경로 총수 8,965 → 8,469, 경로를 가진 사건 500 → 496. 새로 귀속된 42건이
사건 랭킹에 들어오면서 상위 500 의 구성이 바뀐 것이다. 줄어든 것이 아니라
자리를 바꾼 것이고, 4건은 밀려났다.
