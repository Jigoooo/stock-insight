### 13계열 중 3계열만 잰다 — 나머지 열을 왜 뺐는가

**설계에 앞서 정렬을 먼저 쟀다.** `planPriceCorrelations` 계열의 정렬은 날짜를
정확히 교집합한다. 계열별로 관측일이 미국 거래일과 겹치는 비율(2021-08 이후):

```
fred:DGS10 · DGS2       1,256 / 1,305   96.2%   일간   → 쓴다
fred:DEXKOUS              648 /   675   96.0%   일간   → 쓴다
fred:WALCL                258 /   261   98.9%   주간   → 뺀다
fred:ICSA                   0 /   260    0.0%   주간   → 뺀다
월간 8종                   38 /    59   64.4%   월간   → 뺀다
```

- **`ICSA` 는 0이다.** 주간 집계 기준일이 토요일이라 거래일과 절대 안 겹친다.
  넣었으면 조용히 0쌍을 내고 "빌더가 도는데 결과가 없다" 로 보였을 것이다
- **`WALCL` 은 98.9%가 겹치지만 주간이다.** 주 대비 변화를 하루치 주가 수익률과
  맞대는 것은 빈도 불일치다. 주간으로 리샘플한 주가 계열이 있어야 잴 수 있다
- **월간 8종도 같은 이유** 에 표본이 38점뿐이다

계열별 사유는 `MACRO_SERIES_EXCLUSIONS` 에 문자열로 박아 뒀다. 문서에만 적으면
코드를 고치는 사람이 못 본다.

### 수익률 정의를 계열별로 갈랐다

**금리에 수익률 공식을 쓰면 안 된다.** `DGS2` 가 0.10에서 0.20으로 가면 퍼센트
변화로는 +100%가 된다. 금리는 **레벨 차분**(퍼센트포인트), 환율과 주가는
**로그 수익률**. 둘 다 그 자료형의 표준이고, 둘 다 `model_config` 에 이름으로 들어간다.

테스트가 이걸 지킨다: 로그 수익률이 금리 차분의 정확히 -2배인 종목을 만들면
상관이 -1이 나와야 한다. 금리를 수익률로 돌리면 이 등식이 깨진다.

효과는 위 숫자로 이미 알려져 있다.

### 증거를 두 창으로 잡은 이유

`minSourceRevisions: 2` 다. 상관은 **거시 계열 창과 주가 창 둘이 있어야** 생기고,
하나만으로는 재현이 안 된다.

`model_config` 만으로는 안 된다는 것이 중요하다. 마이그레이션 024의
`guard_accepted_relation_revision` 은 적격 증거로 `identity_mapping`·`claim`·
`document`/`chunk`·`source_revision` 만 인정한다 — **`model_config` 는 목록에 없다.**
그것만 달고 accepted 를 넣으면 격리가 아니라 **예외가 나서 퍼블리시 트랜잭션 전체가
롤백된다.** 그래서 빌더는 반드시 `source_revision` 증거를 함께 낸다.

두 창의 리비전은 이 잡이 직접 만든다. `market.macro_vintage` 는 `source_revision_id`
가 일부 행에만 있고(DGS10 은 22,059 중 10,691), `market_ts.ohlcv` 는 계보 컬럼 자체가
없다(research-common 소유, 우리는 읽기만). 있는 것만 골라 인용하면 실제로 쓴 입력을
다른 것으로 적는 셈이라, ETF·프로파일과 같은 방식으로 **쓴 창을 그대로 등록**한다.

**후보를 낸 끝점에만 raw object 를 만든다.** 325종목 전부 매일 찍으면 아무 관계도
인용하지 않는 주가 창을 연 1GB 가까이 쓰게 된다. 후보가 의존하는 13개 안팎만 남긴다.
탈락한 쌍은 raw object 가 아니라 요약의 카운트로 남는다.

### 화면에는 안 나온다 — 일부러

`relation-graph-projector-v2.ts` 의 `DIRECT_PREDICATES` 에 `MACRO_COMOVEMENT` 를
**넣지 않았다.** 넣으면 `peer`(동종) 로 렌더되는데, 거시 계열과 종목의 상관을
"동종 관계" 로 부르는 것은 틀린 말이다. 게다가 그 경로는 양 끝이 다 종목일 것을
요구하므로 Metric 엔티티는 어차피 걸러진다.

즉 이 엣지는 **그래프와 임팩트 경로에는 들어가고 제품 관계 그래프에는 안 나온다.**
화면에 내보내려면 "함께 움직였다" 를 인과로 읽히지 않게 표시하는 별도 설계가 필요하다.

## 이 코드는 이미 라이브다 — 그래서 스킵 가드를 넣었다

**`apps/api/scripts/run_analytics_pipeline.sh:74` 가 매일 07:45 KST 에
`run-v2-graph-publish.ts --apply` 를 라이브 DB 로 실행한다.** 그리고
`stock-insight-analytics.service` 는 워킹 트리를 그대로 돌린다
(`WorkingDirectory=.../stock-insight`, 빌드 이미지가 아니다).

즉 **커밋하는 순간 이 코드는 다음 타이머 발화 때 프로덕션에서 돈다.** 배포를
안 했어도 그렇다. 이걸 늦게 알았다.

그대로 두면 어떻게 되는가: `approvedOntologyIds()` 에 `MACRO_COMOVEMENT` 키가
없고, `persistRelationCandidates` 는 그럴 때 격리가 아니라 **예외를 던진다**
(`no approved predicate ontology revision id configured`). 그리고 이 함수 전체가
그래프 스냅샷과 콘텐츠 팩까지 만드는 **단일 트랜잭션** 안에 있다. 결과는 거시
엣지만 실패하는 게 아니라 **그날 퍼블리시 전체 롤백**이다.

그래서 온톨로지가 승인되기 전에는 단계 전체를 건너뛴다:

```
const macroReady = ontologyIds['MACRO_COMOVEMENT'] > 0
const macroWindows = macroReady ? await load…() : { seriesWindows: [], stockWindows: [] }
```

검사는 `materializeMacroComovementSources` **앞**에 있다 — 건너뛴 실행은 raw
object 도, fetch run 도 만들지 않는다. 요약에는
`"skipped":"ontology_not_approved_migration_066_pending"` 이 찍혀서, 0엣지가
"빌더가 아무것도 못 찾았다"로 오독되지 않는다.

드라이런으로 확인한 현재 상태: `"ontologyApproved":false`. 즉 **지금 타이머가
돌아도 안전하고, 거시 단계는 066 을 적용하는 순간부터 살아난다.**

빈 입력이 후보를 하나도 만들지 않는다는 것은 테스트로 고정했다
(`produces nothing at all from empty windows`).

### 2번이 왜 안 움직이는가 — 근거

두 가지가 각각 막는다.

1. **`loadRecentEvents` 가 `target_entity_id IS NOT NULL` 로 거른다**
   (`run-v2-analytics-publish.ts`). 미귀속 사건은 엣지가 아무리 많아져도 걷기를
   시작하지 못한다. 엣지가 없어서가 아니라 출발점이 없어서다.
2. **`policy_event` 623건이 붙은 Metric 엔티티는 FRED 13계열이 아니다.**

   얻은 것은 `fred:DGS10`·`DGS2`·`DEXKOUS` 다. 서로 다른 노드다.

**5단계가 따로 필요하다** — 시장 어휘에 걸린 사건(34개 용어 · 88매칭)을 해당
`topic` 의 거시 Metric 엔티티에 귀속시키는 것. `analytics.macro_series_topic` 이
이미 계열↔topic 을 잇고 있으니 재료는 있다. 다만 그건 귀속 규칙을 바꾸는 일이고
이번 범위가 아니었다. **범위를 줄인 것이 아니라 처음부터 다른 작업이었고, 이걸
2·3·4의 성공 조건으로 걸어 둔 것이 handoff-2026-08-04 의 오판이다.**

### 3번이 왜 움직일 것으로 보는가

`impact-path-builder.ts` 에서 Stock 이 아닌 노드는 종단이 아니다
(`stockEntityIds.has(edge.objectEntityId)` 일 때만 경로를 닫고, 아니면 계속 걷는다).
그리고 사건의 출발 종목은 종단 집합에서 지역적으로 제거된다. 따라서
**종목A → 거시계열 → 종목B** 가 성립한다. 이건 `CLASSIFIED_AS` 두 번이 아닌
첫 2홉 모양이다.

읽기 전용으로 확인한 두 가지가 이 예측을 뒷받침한다:

1. **`loadSnapshotEdges` 에 술어 화이트리스트가 없다.** 스냅샷 엣지는 전부
   `pathEdges` 가 된다. 즉 엣지만 생기면 워커가 본다 — "엣지는 생겼는데 경로가
   안 쓴다" 는 이 지점 때문은 아니게 된다.
2. **거시 엣지가 붙는 11종목 중 4곳이 45일 창에 사건을 갖고 있다.**
   팬오션 4 · UAL 4 · DAL 1 · PLD 1 = **10건**. 나머지 일곱(TLT·UUP·GLD·XLE·
   HD·XOM·CCJ)은 0건인데, 대부분 ETF 라 뉴스가 안 붙는 것이 당연하다.

**그래서 사거리를 미리 낮춰 적는다: 출발점이 될 수 있는 사건은 10건이다.**
이게 0이었다면 3번 관측은 apply 후에도 안 움직였을 것이고, 그때 "엣지가 안
쓰인다" 로 오독됐을 것이다. 10건은 작지만 0이 아니다.

여전히 **예측이지 관측이 아니다** — apply 전에는 확인할 수 없다.

### 2. apply 후 재측정 — 이 세 쿼리로 닫는다

```sql
-- 관측 1: Metric 엔티티를 지나는 스냅샷 엣지 (지금 0)
SELECT count(*) FROM analytics.graph_snapshot_edge edge
 JOIN core.entity e ON e.entity_id IN (edge.subject_entity_id, edge.object_entity_id)
 WHERE e.entity_type='Metric';

-- 관측 3: 경로가 실제로 밟는 술어
SELECT edge.predicate, count(*)
  FROM analytics.impact_path_v2 path
  CROSS JOIN LATERAL jsonb_array_elements_text(path.explanation->'predicates') AS step(id)
  JOIN analytics.graph_snapshot_edge edge ON edge.graph_snapshot_edge_id = step.id::bigint
 GROUP BY 1 ORDER BY 2 DESC;

-- 술어별 스냅샷 엣지. 이 수는 스냅샷 한 장이 아니라 테이블 전체(스냅샷이 쌓인 것)다.
-- 기준선: PRODUCT_SIMILARITY 38,708 · SAME_ETF_BASKET 38,249 · ISSUED_BY 4,318
--         · CLASSIFIED_AS 2,023 · MACRO_COMOVEMENT 0 · 합 83,298
-- 스냅샷 한 장은 5,379엣지 · 연결 엔티티 651 이다. 둘을 섞어 읽지 말 것 —
-- 나는 아티팩트에서 한 번 섞었다.
SELECT predicate, count(*) FROM analytics.graph_snapshot_edge GROUP BY 1 ORDER BY 2 DESC;
```

### 3. apply 는 두 번 연속 돌려서 확인할 것

`validFrom` 을 관측 창의 마지막 날짜(`lastObservedDate`)로 잡았다.
`PRODUCT_SIMILARITY` 는 이 자리에 `sourceAvailableAt`(항상 현재 시각, 단조 증가)을
쓴다. **내 것은 데이터 날짜라 단조가 아니다** — 주말·휴일에는 같은 값이 반복되고,
vintage 개정으로 겹침 구간이 짧아지면 뒤로 갈 수도 있다.

`corpusDigest` 가 매일 바뀌므로 같은 identity 에 리비전이 계속 append 되는데,
그때 `appendRelationRevision` 이 이전 리비전의 `valid_to` 를 어떻게 닫는지
(마이그레이션 023 의 구간 로직) 확인하지 않았다. **길이 0이거나 뒤집힌 구간이
제약을 건드린다면 첫 실행이 아니라 두 번째 실행에서 터진다.**

일회용 복제 DB에서 066 + `--apply` 를 **연속 두 번** 돌리면 이 질문이 닫힌다.
`stock_insight_qa_marketnews` 를 만들었던 방식이 그대로 쓰인다.

**1·3이 함께 움직여야 산 것이다.** 1만 움직이면 엣지는 생겼는데 경로가 안 쓰는 것이고,
그때는 `MAX_HOPS`·`HOP_DECAY` 나 사건 랭킹의 `connectedEntityIds` 필터를 봐야 한다.

## 이번 세션에 낸 오류 — 같은 순서로 틀리지 않도록

앞선 두 문서의 7가지 + 5가지에 더해:

1. **정렬을 재기 전에 설계할 뻔했다.** 13계열 전부를 대상으로 빌더를 만들려 했는데,
   관측일과 거래일의 겹침을 먼저 재 보니 10계열이 못 쓰는 것이었다. 그대로 갔으면
   빌더는 "정상 동작" 하면서 3계열분만 내고 나머지는 `minOverlappingObservations`
   미달로 조용히 사라졌을 것이다. **조용한 스킵은 오류로 안 보인다**
2. **`adj_close` 를 쓸 뻔했다.** 이름이 맞아 보이지만 주식 1D 298,754행 **전부
   NULL** 이고 `adjustment_version` 도 비어 있다. 컬럼이 있다는 것이 값이 있다는
   뜻이 아니다 — handoff-2026-08-03 오류 6번과 같은 모양
3. **`model_config` 가 증거로 충분하다고 읽을 뻔했다.** 정책의
   `requiresModelConfig` 는 통과시키지만 DB 가드는 인정하지 않는다. 정책 통과와
   가드 통과가 다른 관문이다
4. **superhub 상한이 자르는 게 아니라 버린다.** `evaluateRelationCandidate` 는
   상한 초과 시 트리밍이 아니라 `rejected` 다. 모델 상한을 정책 상한 아래로 두지
   않으면 전량 폐기된다. 테스트로 고정해 뒀다
5. **"배포 안 했으니 안 돈다" 고 생각했다. 틀렸다.** 애널리틱스 타이머는 워킹
   트리를 실행하므로 **커밋만으로 라이브가 된다.** 처음에 잡 스크립트를
   `graph-publish` 로 grep 했는데 npm 스크립트 이름이 `analytics:v2-graph:apply`
   라 안 잡혔고, 그래서 "파이프라인이 이걸 안 부른다" 고 잘못 결론냈다.
   **한 이름으로 grep 해서 안 나오면 없는 게 아니다** — 오류 목록의 "단어 매칭은
   증거가 아니다" 와 같은 모양이다
6. **드라이런이 검증한 것은 산술이지 영속화가 아니다.** 드라이런 경로는
   `persistRelationCandidates`·`ensureSource`·`registerRawObjectWithRevision` 을
   한 번도 부르지 않는다. 18 accepted 는 모델과 정책 판정만 확인한 값이고,
   DB 쪽은 전부 미검증이다. 새 `internal-*` 프로바이더 등록도 최초 세 개 이후
   한 번도 실행된 적이 없는 분기다
7. **아티팩트에서 스냅샷 한 장(5,379)과 테이블 전체(83,298)를 섞었다.**
   5,379 를 낡은 값으로 보고 83,298 로 갈았는데, 5,379 는 지금도 맞는 값이고
   정의가 다른 것이었다. 15배 개선처럼 읽힐 뻔했다
