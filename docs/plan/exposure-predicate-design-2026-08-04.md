# 노출 술어 설계 검토 — 2026-08-04

거시·내러티브 노드를 기업에 잇는 술어를 만들지 검토했다. **만들지 않기를 권한다.**
근거를 설계하려고 재료를 재는 과정에서, 그 술어가 풀려던 문제가 실은 다른 문제라는
것이 드러났기 때문이다.

이 문서는 `roadmap-2026-08-04.md` 의 1·2·3번을 대체한다.

## 검토 순서와 각 단계에서 죽은 가설

### 가설 1 — ownership 빌더를 배선하면 그래프가 넓어진다

구현하고 4단계로 검증했다. 드라이런은 예측과 정확히 일치했다
(HELD_BY 210 · COMMON_OWNER 401 accepted · 2,088 격리 · 초대형 제외 0).
그러나 **연결 증가는 0이었다.**

```
COMMON_OWNER accepted 401쌍   →  이미 SAME_ETF_BASKET 이 잇는 쌍 401 · 새 연결 0
ETF 보유 종목 100개           →  전부 이미 그래프에 있음 · 새로 붙는 종목 0
```

중간에 한 번 "419쌍이 새 연결"이라는 결과가 나왔는데 **틀렸다**.
`public.etf_holdings.entity_id` 는 `public.entities` 공간인데
`core.entity` 와 비교했다 — 오류 목록 5번 그대로다. 파이프라인은
`entities.entity_key` → `core.entity_identifier` 로 변환하고, ETF별 **최신 as_of 한 장만**
쓴다. 그 조건으로 다시 재니 새 연결이 0이 됐다.

코드는 되돌렸다. 호출자 없는 빌더는 실제 결함이지만, 리비전 2,489건과 노드 18개를
늘리면서 목표에 기여가 0인 것을 넣을 이유가 없다.

### 가설 2 — ETF 섹터를 근거로 EXPOSES 를 만든다

`roadmap-2026-08-04.md` 1번이 제안한 근거다. **재료가 없다.**

```
public.etf_holdings.sector  고유값 0 (컬럼이 비어 있다)
```

### 가설 3 — 산업 분류를 근거로 쓴다

**이미 전부 쓰고 있다.** `public.entities.industry_code` 로 해석되는 종목 119개이고,
`CLASSIFIED_AS` accepted 관계가 정확히 119건이다. 남은 여지가 없다.

### 가설 4 — 막힌 사건은 내러티브 노드에 붙어 있다

절반만 맞다. 45일 창에서 연결 안 된 귀속 사건 1,421건의 실체:

| 엔티티 | 사건 | 성격 |
| --- | ---: | --- |
| `us_insider_buys` | 417 | **수집 피드 이름** |
| `us_corporate_events` | 417 | **수집 피드 이름** |
| `gl_major_event` | 258 | **버킷 라벨** |
| `crypto_regulation` | 210 | 버킷 라벨 |
| `tariffs` | 33 | 진짜 내러티브 |
| `narrative_ai_capex` | 32 | 진짜 내러티브 |
| `narrative_semiconductor` | 29 | 진짜 내러티브 |

**1,302건(92%)이 피드·버킷 라벨에 붙어 있다.** 진짜 내러티브는 94건뿐이다.
즉 노출 술어를 완벽하게 만들어도 최대 94건에만 닿는다.

`gl_major_event` 258건을 열어 보면 전부 SpaceX 기사다 — 특정 회사를 지목하는데
회사가 아니라 피드 라벨에 귀속돼 있다.

### 가설 5 — 그러면 재귀속이 답이다

텍스트 귀속 잡(`run-event-text-attribution.ts`)은 `target_entity_id IS NULL` 인 것만
본다. 위 사건들은 **틀린 타깃을 이미 갖고 있어서** 잡의 시야에 안 들어온다.
대상을 넓히면 될 것 같지만, 기존 규칙(이름 4자 이상 단일 매치 / 티커 3자 이상 경계)을
그대로 적용해 재 보면:

```
us_corporate_events   8건 구제 가능 (전부 단일 매치, 안전)
us_insider_buys       5건
합계                 13건 / 1,396건
```

**13건이다.** 나머지가 지목하는 회사가 `core.entity` 에 없기 때문이다.

## 진짜 제약

유니버스가 331종목이고, 뉴스가 다루는 회사는 그보다 훨씬 넓다. 막힌 사건 대부분은
술어가 없어서도, 귀속이 틀려서도 아니라 **그 회사가 시스템에 아예 없어서** 못 닿는다.

이건 수집·유니버스 문제이고, 로드맵 5번(커버리지)의 확장이지 1·2·3번이 아니다.

## 권고

1. **노출 술어를 만들지 않는다.** 최대 사거리가 94건이고, 근거로 쓰려던 재료 둘 중
   하나는 비어 있고 하나는 이미 소진됐다. 남은 유일한 근거 후보는 "섹터에 속하니
   노출됐다"는 해석이고, 그건 이 저장소가 테마 키워드를 거부한 것과 같은 종류다.
2. **텍스트 귀속의 대상을 피드·버킷 라벨 엔티티까지 넓힌다.** 13건은 작지만
   규칙 변경이 아니라 대상 확대이고, 잘못 붙은 귀속을 바로잡는 일이라 순이익이다.
   같이 할 것 — 이 7개 Metric 엔티티가 애초에 사건의 타깃이 되면 안 된다는 것을
   추출기 쪽에서 막아야 재발하지 않는다.
3. **유니버스 확장을 별도 항목으로 세운다.** 지금 로드맵에 이 항목이 없다.
   이것이 "종목 이름이 없는 시장 뉴스가 종목에 닿는" 문제의 실제 상류다.
