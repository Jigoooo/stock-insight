## 이번 조사가 새로 밝힌 것

앞선 두 감사는 **표면별 수율**(상류 → 뷰)과 **사슬**을 쟀다. 그 지표로는
`v2 임팩트 → 제품` 사슬이 "끊긴 곳 없음"으로 건강하게 보인다. 이번에는 그 경로가
**실제로 무엇을 밟는지**를 처음 쟀고, 거기서 다른 그림이 나왔다.

### 1. 경로가 밟는 술어는 셋뿐이다

```
1홉  SAME_ETF_BASKET      66,825회   통계 — "같은 ETF에 들어 있다"
1홉  PRODUCT_SIMILARITY   36,303회   통계 — "제품이 비슷하다"
2홉  CLASSIFIED_AS         4,914회   구조 — A→분류←B 공통 소속
```

`AFFECTS`·`SUPPLY_CHAIN`·`OWNS`·`EXPOSES`·`PEER_OF`·`SAME_INDUSTRY`·`SAME_THEME`
는 **한 번도 밟히지 않는다**. 전부 증거 부족으로 격리(3,312건)돼 스냅샷에 못 들어간다.

측정 방법: `impact_path_v2.explanation->'predicates'` 는 `graph_snapshot_edge_id`
배열이다(고유값 18,931 > relation_identity 8,678, entity 최대 1,493 로 식별). 그 엣지를
`graph_snapshot_edge.predicate` 로 풀었다.

### 2. 다중 홉은 2홉까지, 3홉 이상은 0건

```
봉인 경로 105,585   1홉 103,128 (97.7%) · 2홉 2,457 · 3홉 이상 0
```

2홉도 `CLASSIFIED_AS` 두 번이라 "A가 B에, B가 C에 영향"이 아니라 "A와 B가 같은 분류"다.
다중 홉 배관은 있는데 밟을 인과 엣지가 없다.

### 3. 기업이 안 붙은 사건이 만든 경로는 0건

### 5. 커버리지 미수집 — 조사 완료 (2026-08-04) · 고칠 코드가 없다

**수집기는 정상 작동 중이고, 제약은 OpenDART 일일 한도와 시간이다.**

미수집 셀을 이유별로 가르면 대부분이 실패가 아니라 밀린 것이다.

| 상태 | 셀 | 이유 |
| --- | ---: | --- |
| `complete` | 1,613 | |
| `not_collected` | **1,587** | **커서가 아직 이 발행사에 도달하지 않음** |
| `not_applicable` | 364 | 아직 오지 않은 기간 |
| `source_unavailable` | 71 | OpenDART status 013 — 물었고 없음 |
| `not_collected` | 5 | 빈 응답을 버리던 시절의 잔재. 다음 방문에 자가 치유 |

`quotaExhausted` 는 추론이 아니다. OpenDART 가 **status `020`(요청 제한 초과)** 를
반환할 때만 켜진다(`run-dart-financial-facts.ts:257`). 일일 한도를 잡 자신의
기록으로 재면:

```
2026-08-04  실행 1회  300 요청  소진 안 됨
2026-08-03  실행 8회  361 요청  소진됨       ← 한도는 (300, 361] 사이
2026-08-02 이전       100 요청/일  소진 안 됨
```

`--limit` 은 요청 수가 아니라 **발행사 수**다. 15 발행사 × 5년 × 4보고서 = 300요청으로
정확히 맞는다. 즉 하루에 처리 가능한 발행사는 한도 나누기 20 = **최대 18곳**이다.

커서는 182곳 중 **111곳**까지 왔다. 남은 71곳을 하루 15곳씩 처리하면 **약 5일**이면
커서 한 바퀴가 끝난다. 발행사당 요청 수(20)는 연도·보고서 조합이 정하므로 줄일 수
없고, 하루 15 → 17곳으로 올리면 한도를 더 쓰지만 실행 중간에 020을 맞아 `partial`
로 끝날 위험이 커진다. 이득 13%에 실패 흔적을 남기는 교환이라 하지 않는다.

**닫는 관측**: `nextOffset` 이 182에 도달하고 `not_collected` 의 "커서 미도달"
사유가 0이 된다. 그때 남는 미수집은 성격이 다른 것뿐이다.

미귀속 사건이 만든 경로가 0을 벗어난다 — 는 2·3·4단계가 아무리 잘 돼도 안 움직인다.

붙어 있는 Metric 엔티티는 `gl_major_event`·`crypto_regulation` 등으로 **FRED 13계열과
다른 노드**다. 시장 어휘에 걸린 사건을 거시 Metric 엔티티에 귀속시키는 5단계가
따로 필요하다. 범위를 줄인 것이 아니라 처음부터 다른 작업이었다.

#### 만들 것

1. ~~**마이그레이션**~~ **완료.** 13개 계열을 `core.entity`(`entity_type='Metric'`)로 등록하고
   `core.entity_identifier` 에 `FRED_SERIES` 식별자를 단다. `market_topic_term.topic`
   과의 대응은 이 단계에서 테이블로 둔다 — 코드가 아니라 행이어야 틀린 매핑이
   배포가 아니라 삭제가 된다
2. **정책** — `relation-policy.ts` 에 새 술어. `relationClass: 'association'`,
   `requiresModelConfig: true`, `minSourceRevisions: 1`, superhub 캡 필요.
   `PRODUCT_SIMILARITY` 항목을 그대로 본뜬다
3. **빌더** — `relations/builders/` 에 추가. `product-similarity.ts` 와
   `product-similarity-model.ts` 의 분리를 따른다(모델 계산과 후보 생성이 별개 파일)
4. **배선** — `run-v2-graph-publish.ts` 의 기존 세 빌더 옆에 붙인다

#### 반드시 model_config 에 묶을 것

창 길이 · 상관 임계값 · 계열 id · 수익률 정의 · 표본 최소 길이. 하나라도 빠지면
재실행이 안 되고, 재실행이 안 되면 반박할 수 없고, 반박할 수 없으면 그건 주장이다.

#### 얻는 것과 얻지 못하는 것 — 먼저 적는다

- **얻는다**: "종목 이름 없는 시장 뉴스가 종목에 닿는 길". 지금 미귀속 2,454건과
  어휘 매칭 88건이 어디에도 닿지 않는 상태를 처음으로 푼다
- **얻지 못한다**: 인과. 이건 통계적 엣지이고 `SAME_ETF_BASKET` 과 같은 층위다.
  "타고타고타고" 의 인과 경로는 여전히 7번(공급망)뿐이다

상관을 인과로 읽히게 표시하면 안 된다. 화면 문구와 술어 이름 양쪽에서
"함께 움직였다" 이상을 주장하지 말 것.

#### 닫는 관측

- 13개 계열 엔티티가 스냅샷 엣지를 갖는다(지금 Metric 엔티티의 엣지는 0개)
- 미귀속 사건이 만든 임팩트 경로가 0을 벗어난다
- 경로가 밟는 술어 목록에 새 술어가 등장한다. 앞의 둘만 움직이고 이게 안 움직이면
  엣지는 생겼는데 경로가 안 쓰는 것이다

### 7. 공급망 공시 수집 — 새 항목 (1~5 재검토에서 드러남)

**인과 술어를 정당하게 얻는 유일하게 남은 경로다.** 위 3번에서 "인과 술어는 정책이
없다"고 적었는데 틀렸다. `SUPPLIES`·`CUSTOMER_OF` 는 다 갖춰져 있고 데이터만 없다.

```
정책    ✓  relation-policy.ts · promotionEligible true · minSourceRevisions 1
빌더    ✓  relations/builders/supply-chain.ts — 호출자 없음
테이블  ✓  analytics.firm_supply_relation
데이터  ✗  0행
```

빌더가 요구하는 것은 `SupplyChainObservation`
(`supplierEntityId`·`customerEntityId`·`disclosureKind`·`sourceRevisionId`·
`availableAt`·`validFrom`)이고, 핵심은 **공시된 것만** 받는다는 점이다 —
`absenceSemantics: unknown_not_disclosed`, 공시가 없으면 아무것도 만들지 않는다.
지어내기가 구조적으로 막혀 있어서, 이 저장소가 거부해온 종류의 추론이 아니다.

후보 원천은 SEC 10-K 의 주요 고객 공시와 DART 의 매출처 공시다. **어느 쪽도 아직
확인하지 않았다** — 수집 가능성과 파싱 난이도를 재는 것이 첫 단계다.

`watchlist.customers` 는 후보가 아니다. 8행이고 열어 보면 Discord 사용자
목록이며 research-common 소유다. 이름만 겹친다 — 오류 목록 2번 그대로다.

**닫는 관측**: `firm_supply_relation` 이 0을 벗어나고, 경로가 밟는 술어 목록에
`SUPPLIES` 가 처음 등장한다. 후자까지 가야 실제로 산 것이다.
